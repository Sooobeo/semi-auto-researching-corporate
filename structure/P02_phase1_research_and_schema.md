## 3. 상세 설계와 판단 규칙

### 문헌을 읽는 목적

‘논문을 몇 개 읽었다’가 완료 조건이 아니다. 각 문헌이 사건 단위, 필드, 라벨, 평가 또는 지표 정의 중 어떤 설계 결정을 바꾸는지 한 줄로 연결한다. 초록만 읽은 문헌과 본문을 정독한 문헌의 상태를 분리한다. [R02/R04/R05](REFERENCES.md)는 서로 언어·과업이 다르므로 성능을 같은 표에서 우열로 해석하지 않는다.

### 분석 단위 후보

문서(입력), 근거 블록(문장·표 위치), event mention(개별 주장), event cluster(같은 발표의 재보도), revision relation(정정·후속)으로 구분한다. 한 문서에 회사·제품·시점이 여러 개이면 다른 주장으로 분리한다. 같은 발표를 옮긴 기사 수를 독립 사건 수로 집계하지 않는다. 사건이 여러 근거 문장을 요구하면 evidence 배열을 허용한다.

### 중요성은 사실 추출과 다른 층

기록을 facts와 assessments로 나눈다. facts는 원문의 회사·제품·수치·시점·계획 여부다. assessments는 어떤 기존 가정이 달라지는가, 추가 검토가 필요한가, 판단 근거가 충분한가다. 주가 상승/하락, 뉴스 감성, 회계상 중요성, 리서치 검토 행동은 서로 다른 개념이다. 단일 점수/순서 등급/다차원 질문은 후보로 유지하고 P3 일치도와 P5 효용을 본 뒤 선택한다.

### 필수 의미 구별

실적 기간(reference period), 발표 시점(published at), 적용 예정 시점(effective period), 시스템이 관측한 시점(observed at)을 따로 저장한다. 현재 알려진 정정 수치를 과거 판단에 사용하지 않는다. ‘확정’은 회사가 실행했다고 발표했다는 뜻과 외부 검증이 끝났다는 뜻을 구별하여 reported modality와 evidence status를 따로 둔다.

### 예시부터 설계 검증

[C01/C02](REFERENCES.md)의 계획→실행 사례를 두 event mention으로 기록하고 follow_up 관계를 붙인다. 원문의 출하와 판매를 동일 수량으로 바꾸지 않는다. 비교할 prior event를 찾지 못하면 prior_not_found로 남긴다. 근거 없이 ‘상향’이나 ‘중요’로 라벨링하지 않는다.

공통 스키마의 정확한 필드·누락 규칙은 [DATA_CONTRACTS](DATA_CONTRACTS.md)를 사용한다. 이 문서의 후보가 변경되면 스키마 버전과 변환 여부를 결정 기록에 남긴다.

## 6. 단계 종료와 다음 단계 전달

**종료 기준:** 선행연구 map과 스키마·가이드를 다른 팀원이 읽고 새로운 실제 사례를 기록할 수 있다. 미결 사항을 삭제하지 않고 다음 연구 작업으로 연결한다.

**인계:** P2에 정의·선정 원칙, P3에 사건 단위·필드·질문·가이드 초안을 전달한다.

결과 기록에는 완료 작업 ID, 산출물 경로·버전·hash, 실제 건수, 검증 결과, 검토 역할, 남은 문제와 후속 작업을 남깁니다. 미실행 검증을 통과로 표시하지 않습니다. 성능 목표·예산·표본 수 변경은 [결정 기록](DECISIONS.md)에 남깁니다.
