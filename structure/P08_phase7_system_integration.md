## 1. 이 단계에서 답할 질문

소수 미국 기업의 문서와 필요한 사업 관계가 검토 카드로 이어지고, 사람이 영어 원문과 변경 이유·불확실성을 확인하고 수정할 수 있는가?

- **책임 역할 후보:** C 통합·화면·운영, B 파이프라인·검색 연결, A 카드 검증·사용성. A/B/C는 미배정 역할 자리이며 기업별 담당이나 인원 수를 확정하지 않습니다.
- **착수 조건:** 미국 자료로 새로 구성·검증한 P4 extractor, P5 기본 중요성 정책, P6 change/scenario interface. 각 단계의 버전·오류 스키마가 고정.
- **범위:** 로컬 MVP·배치 실행·카드·수정로그·active learning 후보 큐. 사업 관계는 변화의 맥락과 추가 확인 질문에 필요한 범위로 연결한다. 기업 페이지·테마/관계 그래프·상시 갱신 웹사이트·신규 기업 발굴 기능을 필수 결과물로 추가하지 않는다. 자동 거래·투자 추천·외부 알림·공개 배포는 현재 범위에 포함하지 않는다.
- **연결 에픽:** [KAN-11](https://qyurimoon.atlassian.net/browse/KAN-11)은 기존 작업 연결 참고입니다. 새 대상의 담당·기한 배정은 별도 결정합니다.

## 3. 상세 설계와 판단 규칙

### 배치 우선 통합

폴더나 등록된 URL 목록을 입력받아 수집→추출→표준화→검색→변화→중요성→카드를 실행한다. 초기에는 수동 실행 가능한 batch로 충분하다. 입력 한 건의 실패가 전체 run을 중단하지 않도록 stage별 성공/실패/skipped/retryable을 저장한다. 스케줄러·클라우드 배포는 실제 필요를 확인한 뒤 별도 작업으로 둔다.

영문 원문·원문 ID·근거 위치를 기준 입력으로 유지한다. 한국어 검토 설명은 별도 요약/번역 층이며 수치·modality·관계 방향을 원문에 대조한다. 무료 자료와 보유 자원을 우선 사용하되 처리량·실행시간·운영 비용은 실제 측정한다. 외부 API·LLM 경로는 해당 원문·파생 데이터의 저장·AI 입력·외부 전송 권리와 비용을 확인한 경우에만 설정한다.

### 멱등성과 resume

문서 hash + source revision + parser/model/registry/policy version을 stage key로 사용한다. 같은 입력·설정 재실행은 카드 중복 생성 대신 같은 결과를 재사용한다. 설정이 바뀌면 새 run을 만들고 이전 결과를 보존한다. 외부 API 재시도와 사용자 feedback 제출은 별도 idempotency key를 가진다.

### 카드의 정보 순서

회사·사업범위·제품 → 새 발표 주장 → 이전 정보와 차이 → 이전/새 원문 근거 → 필요한 사업 관계 맥락 → 검토 우선순위 이유 → 불확실성과 확인 질문 → 선택적 시나리오 순서다. raw score·모델 내부 용어는 기본 화면에 노출하지 않고 자세히 보기로 둔다. ‘계산 불가’도 왜 불가한지 보인다. 추출 confidence·prior 적합성·materiality confidence를 하나의 확률처럼 합치지 않는다.

`review_readiness`는 `supported`(근거 확인), `needs_review`(추가 확인 필요), `not_comparable`(비교 어려움)와 이유로 표시한다. 이는 `evidence_status`와 다른 검토 상태이며 supported는 원문이 해당 주장·연결을 지지한다는 뜻이다. 기업 발표나 검토자 합의를 원문 밖의 진실 보장으로 표현하지 않는다. 근거 있는 관계 사실, 실적 영향에 대한 assessment, 수식·가정에 따른 derived 결과는 카드에서 구분한다. 예를 들어 가상 기업 A의 고객 B 계약 축소는 계약 변화로 보여주고 공개 수치가 없으면 매출 감소 규모는 추가 확인 질문으로 남긴다.

회계연도/분기 이름과 실제 대상 기간, 발표 시각·출처 시간대·DST·정밀도, 적용 시점을 구분해 보여준다. USD를 포함한 원문 통화·scale·전사/segment·GAAP/non-GAAP 정의와 비교 불가 이유를 확인할 수 있어야 한다. 다단계 관계만으로 실적·주가 영향이나 거래 판단을 생성하지 않는다.

### 사용자 행동

확인, 사실 수정, 무관, 추가조사, 가정 수정의 버튼/입력 흐름을 둔다. 수정은 기존 예측을 덮어쓰지 않고 actor·시간·card_version·변경 필드·근거를 append한다. 단일 사용자 수정은 즉시 gold나 모델 학습자료가 아니라 검토 후보로 들어간다. Test 사건의 feedback은 현재 학습 주기에서 격리한다.

### 상태와 영속 저장

Streamlit은 후보 UI다. [T08](REFERENCES.md)의 session state·cache와 영속 store를 구분한다. 새로고침·다른 세션에서도 확정한 검토 결과가 보존되도록 DB에 저장한다. 캐시는 사용자/데이터 버전/권한 범위를 키로 분리하고 비공개 자료가 다른 사용자에게 노출되지 않게 한다. 로컬 시연에서도 API 키·전체 제한 원문을 화면 로그에 출력하지 않는다.

### 운영 관측

run별 입력 수, 단계별 통과/실패, card 수, 중복 재사용, 처리시간, LLM 호출·비용, 검토·수정 수를 집계한다. ‘0건 카드’가 정말 관련 사건 없음인지 수집 실패인지 구분한다. 수집 원문은 신뢰할 수 없는 데이터이므로 그 안의 문장을 코드·명령·모델 시스템 지시로 실행하지 않는다.

### 같은 카드에서 개인 분석 메모로 연결

[공통 목표·리서치 적용 흐름](GOALS_AND_RESEARCH_WORKFLOW.md)에 따라 공통 카드에 선정 재무 개념·계산/대사·가정 참조를 연결하고 개인 적용 `analyst_memos.jsonl`은 같은 카드·원문을 재사용한다. 메모는 질문·실적/사업 해석·가정 변화·대안 설명·불확실성·다음 확인으로 구성하며 작성자·검토자·수정 이력을 남긴다.

카드와 기존 로컬 검토 흐름을 유지하며 별도 메모 화면이나 모든 팀원의 메모 작성을 필수로 추가하지 않는다. 개인 재무 적용 담당과 팀원의 온톨로지/NLP/사업 분석 기여는 각각 기록한다. agent 초안, 사람의 채택/수정, 검토 완료를 구별하고 메모를 자동으로 gold·학습자료로 승격하지 않는다. 계산 불가인 사업 관계 카드도 정상적으로 보존한다.

## 5. 필수 검증 시나리오

- [ ] 개인 메모에서 공통 카드·원문·재무 계산/대사·가정으로 이동할 수 있고 agent 초안·사람 수정·검토 이력이 구분된다.
- [ ] 메모·재무 영향 숫자가 없는 사업 관계 카드도 근거·불확실성·추가 확인을 유지한다.

- [ ] 같은 문서를 두 번 실행해도 동일 버전 카드가 중복되지 않는다.
- [ ] 도중 실패 후 이어서 실행한 결과가 전체 재실행과 논리적으로 같다.
- [ ] 수정·새로고침 후 기록이 유지되고 원예측을 볼 수 있다.
- [ ] 원문 속 지시 문장이 시스템 실행 지시로 취급되지 않는다.
- [ ] 카드0건 화면에서 정상 무관 결과와 처리 실패를 구분한다.
- [ ] supported 상태도 원문 밖의 진실 보장으로 표시되지 않는다.
- [ ] 관계 사실·영향 해석·계산 결과와 세 readiness 상태를 구별할 수 있다.
- [ ] 미국 회계기간·통화·scope 불일치가 카드의 비교 불가 이유로 유지된다.

## 6. 단계 종료와 다음 단계 전달

**종료 기준:** 허용된 샘플에서 수집→카드→검토 기록이 실제 실행되며 오류·재시도·영속 저장을 확인했다. 실제 운영 가이드와 알려진 한계를 남긴다.

**인계:** P8에 고정 MVP 버전·사용자 과업·측정 로그·데모 입력을 전달한다. 연습 자료와 test를 분리한다.

결과 기록에는 완료 작업 ID, 산출물 경로·버전·hash, 실제 건수, 검증 결과, 검토 역할, 남은 문제와 후속 작업을 남깁니다. 미실행 검증을 통과로 표시하지 않습니다. 성능 목표·예산·표본 수 변경은 [결정 기록](DECISIONS.md)에 남깁니다.

## 7. 이 단계의 레퍼런스

- **T05 · [SQLite FTS5](https://www.sqlite.org/fts5.html)** — 희소 검색·BM25·인덱스·토큰화 구현 후보. 영문 기업/제품명·숫자·단위는 새 표본에서 검증한다.
