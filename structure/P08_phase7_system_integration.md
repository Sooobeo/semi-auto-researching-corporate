## 1. 이 단계에서 답할 질문

수집된 문서가 실패·중복 없이 검토 카드로 이어지고, 사람이 원문과 변경 이유를 확인하고 수정할 수 있는가?

- **책임 역할:** C 통합·화면·운영, B 파이프라인·검색 연결, A 카드 검증·사용성
- **착수 조건:** P4 extractor, P5 기본 중요성 정책, P6 change/scenario interface. 각 단계의 버전·오류 스키마가 고정.
- **범위:** 로컬 MVP·배치 실행·카드·수정로그·active learning 후보 큐. 자동 거래·외부 알림·공개 배포는 포함하지 않는다.
- **연결 에픽:** [KAN-11](https://qyurimoon.atlassian.net/browse/KAN-11). 실명·기한은 팀이 배정하며 여기서는 역할 기준으로 작성합니다.

## 3. 상세 설계와 판단 규칙

### 배치 우선 통합

폴더나 등록된 URL 목록을 입력받아 수집→추출→표준화→검색→변화→중요성→카드를 실행한다. 초기에는 수동 실행 가능한 batch로 충분하다. 입력 한 건의 실패가 전체 run을 중단하지 않도록 stage별 성공/실패/skipped/retryable을 저장한다. 스케줄러·클라우드 배포는 실제 필요를 확인한 뒤 별도 작업으로 둔다.

### 멱등성과 resume

문서 hash + source revision + parser/model/registry/policy version을 stage key로 사용한다. 같은 입력·설정 재실행은 카드 중복 생성 대신 같은 결과를 재사용한다. 설정이 바뀌면 새 run을 만들고 이전 결과를 보존한다. 외부 API 재시도와 사용자 feedback 제출은 별도 idempotency key를 가진다.

### 카드의 정보 순서

회사·사업범위·제품 → 새 사실 → 이전 정보와 차이 → 이전/새 원문 근거 → 중요성 판단 이유 → 불확실성과 확인 질문 → 선택적 시나리오 순서다. raw score·모델 내부 용어는 기본 화면에 노출하지 않고 자세히 보기로 둔다. ‘계산 불가’도 왜 불가한지 보인다. 추출 confidence·prior 적합성·materiality confidence를 하나의 확률처럼 합치지 않는다.

### 사용자 행동

확인, 사실 수정, 무관, 추가조사, 가정 수정의 버튼/입력 흐름을 둔다. 수정은 기존 예측을 덮어쓰지 않고 actor·시간·card_version·변경 필드·근거를 append한다. 단일 사용자 수정은 즉시 gold나 모델 학습자료가 아니라 검토 후보로 들어간다. Test 사건의 feedback은 현재 학습 주기에서 격리한다.

### 상태와 영속 저장

Streamlit은 후보 UI다. [T08](REFERENCES.md)의 session state·cache와 영속 store를 구분한다. 새로고침·다른 세션에서도 확정한 검토 결과가 보존되도록 DB에 저장한다. 캐시는 사용자/데이터 버전/권한 범위를 키로 분리하고 비공개 자료가 다른 사용자에게 노출되지 않게 한다. 로컬 시연에서도 API 키·전체 제한 원문을 화면 로그에 출력하지 않는다.

### 운영 관측

run별 입력 수, 단계별 통과/실패, card 수, 중복 재사용, 처리시간, LLM 호출·비용, 검토·수정 수를 집계한다. ‘0건 카드’가 정말 관련 사건 없음인지 수집 실패인지 구분한다. 수집 원문은 신뢰할 수 없는 데이터이므로 그 안의 문장을 코드·명령·모델 시스템 지시로 실행하지 않는다.

**종료 기준:** 허용된 샘플에서 수집→카드→검토 기록이 실제 실행되며 오류·재시도·영속 저장을 확인했다. 실제 운영 가이드와 알려진 한계를 남긴다.

**인계:** P8에 고정 MVP 버전·사용자 과업·측정 로그·데모 입력을 전달한다. 연습 자료와 test를 분리한다.

결과 기록에는 완료 작업 ID, 산출물 경로·버전·hash, 실제 건수, 검증 결과, 검토 역할, 남은 문제와 후속 작업을 남깁니다. 미실행 검증을 통과로 표시하지 않습니다. 성능 목표·예산·표본 수 변경은 [결정 기록](DECISIONS.md)에 남깁니다.
