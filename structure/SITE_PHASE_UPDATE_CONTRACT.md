## 3. 데이터 내보내기 계약

Phase마다 내보내기 adapter와 schema를 함께 갱신한다. 기존 `web/p05/snapshot.py`는 P05 결과용이며 새 Phase 데이터를 경로만 바꾸어 넣지 않는다.

게시 데이터에는 Phase/run ID, 생성 시각, 실제 입력 범위, 원문 사실의 허용된 숫자·표준 라벨·기간·위치, 템플릿으로 작성한 검토 사유, 비교/계산 조건·상태·분모, 실행 버전만 포함한다. `raw HTML`, 제한된 본문·연차보고서 prose, private 경로, 키·토큰, 개인 메모 원문, 미검증 자유입력은 기본 게시 대상에서 제외한다. 원문 링크가 있다는 이유로 원문 전체 복제 권리가 있다고 가정하지 않는다.

실행 전 출처 조건과 해당 필드의 외부 전송·공유 범위를 확인한다. 기존의 최소 숫자·표준 라벨·기간·위치 내보내기 범위를 넘어가는 자료는 별도 권리 근거 없이 추가하지 않는다. 후보의 `needs_review`, null·실패·보류와 독립 평가 미실행을 내보내기에서 제거하지 않는다.

금액·비율은 Decimal 원 문자열을 유지한다. 화면에서는 scale을 다시 곱하지 않으며 0, 미상, 해당 없음, 실패를 구별한다. 화면에 표시하는 변화·파생값에는 입력 참조와 공식·정의가 있어야 한다.

## 4. 로컬 실행과 공유 화면

기본 운영은 **내 PC에서 실행 → 검증된 결과를 내보내기 → 같은 사이트에 게시 → 두 사람이 조회**다. 공유 사이트의 버튼으로 사용자 PC의 Python을 실행할 수 있다고 안내하지 않는다.

공유 화면에 실행·동시 저장 기능을 추가하려면 실제 인증된 서버 실행, 영속 저장과 충돌 처리까지 구현·검증해야 한다. 현재는 그 기능을 가정하지 않는다. 브라우저 session state나 localStorage만으로 두 사람이 공동 저장했다고 표현하지 않는다. P08의 기본 피드백 경로는 파일 내보내기·소유자 가져오기·재게시로 명시한다.

## 5. 갱신 순서

1. 현재 active run과 upstream 동결 hash를 확인하고 새 Phase 실행 결과를 검증한다.
2. 같은 `web/p05/`에 화면과 Phase adapter를 갱신한다. 이전 Phase 결과의 조회와 핵심 상태 표시를 유지한다.
3. 게시 allowlist·schema·ID 참조·분모·미상 상태·수치 표시를 검사한다. 실행 기능을 바꿨다면 로컬 API와 실패 경로를 확인한다.
4. 가능하면 브라우저에서 주요 목록/필터/상세·좁은 화면·빈 결과/실패를 확인한다. 브라우저가 제공되지 않으면 `browser_qa=not_performed`와 대체 검증을 기록하며 통과로 표시하지 않는다.
5. Sites의 기존 프로젝트를 조회하고 기존 접근 범위를 유지한다. 제공되는 Sites 게시 워크플로로 **같은 프로젝트**의 새 버전을 저장·배포한다. 로컬 HTML 수정이나 GitHub push만으로 게시 완료로 처리하지 않는다.
6. 배포 도구가 반환한 배포 상태·URL·버전·commit을 기록한다. 최종 상태가 성공인지 확인한다. 배포 결과 확인을 위해 제한된 원문이나 인증 토큰을 로그에 출력하지 않는다.
7. Phase 인계 문서와 브리핑에 사이트 반영 내용·게시 버전·남은 문제를 적는다.

로컬 source 준비와 배포 작업은 Sites skill의 현재 워크플로를 따른다. 도구 자격증명은 메모리에서만 사용하고, 배포용 임시 checkout은 원문/private 파일과 분리한다. 같은 사이트를 대상으로 한 업데이트는 이번 요청으로 실행 범위에 포함됐으므로 매 Phase마다 다시 게시 승인을 요구하지 않는다.

## 6. Phase마다 남길 게시 기록

`artifacts/us_equity/pN/runs/<run_id>/site_update_manifest.json`에 다음을 기록한다. 값이 아직 없으면 null과 사유를 남긴다.

```text
phase_id, pipeline_run_id, source_run_refs, source_output_hashes,
snapshot_schema_version, snapshot_sha256, exported_record_counts,
project_id, site_url, access_scope_checked_at, access_change_performed,
local_checks, browser_qa, browser_qa_reason,
site_source_commit, site_version_id, deployment_id,
deployment_status, deployed_at, publication_error
```

실행 출력은 먼저 동결하고 게시 기록은 별도 파일로 관리해 배포할 때마다 계산 결과의 hash가 변하지 않게 한다. 배포용 archive에는 이 기록의 민감정보나 private 파일이 들어가지 않아야 한다.

## 7. 완료 판단

코드·artifact·검증·내보내기·화면 업데이트가 준비되고, 같은 프로젝트에 새 버전의 게시 성공을 확인해야 ‘사이트 반영 완료’다. 실패하면 마지막 정상 게시 버전과 신규 게시 실패를 모두 기록한다. 미게시 결과를 현재 사이트에서 볼 수 있다고 브리핑하지 않는다.

이 계약은 향후 Phase 실행 때 갱신하는 규칙이다. 일정에 따른 자동 수집·자동 실행·자동 배포를 설정한 것은 아니다.
