## 1. 이번에 만들 것

**내 PC에서 한 번 실행하면 추출 → 이전 정보 검색·비교 → 검토 사유 → 검토 카드까지 이어지고, 두 사람이 같은 게시 결과를 보며 확인·수정·추가조사 기록을 남길 수 있는 흐름을 만든다.** 실패한 단계와 부족한 근거도 카드와 실행 현황에서 확인할 수 있어야 한다.

사용자는 ‘무슨 발표인가 → 이전과 어떻게 다른가 → 근거는 어디인가 → 무엇을 더 확인할까’를 한 화면에서 읽는다. 전체 원문을 이해한 사람의 판단과 프로그램의 추출·계산 결과를 구분한다.

P06/P07의 개발 계약이 준비되면 중요성 모델·독립 benchmark가 미완료여도 통합 개발을 진행한다. 입력 계약이 구현되지 않았다면 해당 stage를 `skipped_missing_dependency`로 기록하고 통합 성공이라고 보고하지 않는다.

## 3. 기본 운영 구조

```text
등록·검증된 로컬 입력
  → P05 추출/검증
  → P07 prior·비교·계산/중단
  → P06 검토 사유 + 이용 가능한 change 연결
  → 검토 카드 구성/검증
  → 안전한 snapshot → 같은 지정 사용자 사이트에 게시

게시 화면의 검토 기록 파일 내보내기
  → 소유자의 로컬 가져오기/검증 → 새 검토 revision
  → 업데이트 snapshot 재게시
```

첫 구현은 검증된 기존 입력을 처리하는 batch다. 새 URL을 입력받더라도 출처·권리·자동 접근·저장·외부 전송 조건을 확인한 등록 자료만 처리한다. 수집 확대·스케줄 실행·외부 알림·외부 LLM은 현재 기본 경로에 포함하지 않는다. 입력 문서 안의 지시문은 데이터이며 실행 명령이 아니다.

P07 후속 feature를 사용한 P06 정책은 원래 정책을 수정하지 않고 새 버전으로 등록한다. `P06 기본 목록 → P07 개발 → P06 change 연결`의 개발 순서와, 한 배치 안의 `P07 → P06 연결 → 카드` 실행 순서를 구분해 순환 의존성을 없앤다.

## 4. 실행·실패·재개 계약

`pipeline_spec.md`에 stage의 입력/출력 schema·버전·ID·오류·해시·권리 조건을 고정한다. 설정은 비밀값이 없는 `run_config.json`으로 시작한다. 기존 연구 설계의 YAML은 필수 포맷이 아니며 현재 구현과 실제 설치 환경에 맞춘다.

stage key는 입력 내용 hash·source revision·코드/추출기/registry/정책/schema 버전을 포함한다. 새 정책이나 입력은 새 결과로 저장한다. 같은 key의 성공 결과는 재사용하되 다른 사용자의 검토 이력을 덮어쓰지 않는다.

- stage 상태: `succeeded / failed / skipped / retryable / reused`와 reason.
- 항목 상태: 정상 후보·보류·비교 불가·실패를 원래 입력 ID에 연결.
- 재개: 성공한 stage의 hash를 다시 확인한 뒤 실패/미실행 stage부터 진행.
- 장애: 한 항목 실패를 전체 정상 카드처럼 표시하지 않으며 다른 항목은 가능한 범위에서 계속 처리.
- 취소/timeout: 실제 실행 상태·부분 출력·마지막 성공 stage를 남기고 active run으로 승격하지 않음.

입력 수는 stage별 `입력 = 정상 + 실패 + 보류/제외` 관계를 그 stage의 단위에 맞게 검사한다. 후보 39개가 카드 39개로 반드시 이어지는 것은 아니다. 관계 공유 근거·검토 목적에 따라 묶을 수 있으므로 candidate→card 연결표와 집계 단위를 남긴다.

코드는 `scripts/p08_*.py` 또는 새 통합 모듈에 작성한다. 동결된 P05 코드에 통합용 함수나 파일을 추가하지 않는다. 기존 CLI 호출은 허용된 고정 명령과 입력/출력 경로로 제한하고 사용자 문자열을 shell 명령으로 조합하지 않는다.

## 5. 카드의 내용과 읽는 순서

`review_card_schema.json`과 `review_cards.jsonl`은 [공통 규약](DATA_CONTRACTS.md)의 필드를 현재 P05/P06/P07 adapter로 연결한다. 아직 없는 event ID나 정답 ID를 추측하지 않는다. 후보 기반 내부 카드 ID와 원래 candidate/family/문서/revision 참조를 명시한다.

1. 회사·사업 범위·실제 대상 기간·발표 날짜.
2. 새 발표 주장과 허용된 숫자/관계.
3. 이전 정보·검색 모드·기준 시점과 차이.
4. 양쪽 원문 위치·표 머리글·정의와 비교 조건.
5. 검토 사유·부족한 근거·추가 확인 질문.
6. 가능한 계산의 입력·공식·조건, 또는 계산 불가 이유.
7. 사람의 확인/수정·가정/메모가 있다면 별도 이력.

원문이 발표한 것, 사람이 해석한 것, 공식으로 계산한 것을 화면에서 구별한다. 한국어 설명은 숫자·부정·modality·방향을 바꾸지 않는 템플릿부터 사용한다. 원문 전체를 외부 LLM에 보내 생성한 요약이 있다고 가정하지 않는다.

`review_readiness`, `evidence_status`, `pipeline_status`, materiality 판단은 각각 유지한다. 비교 불가가 있으면 비교 목적의 `not_comparable`과 이유를 표시하고, 필요한 문맥이 미상인 경우 `needs_review`를 유지한다. supported를 쓸 경우 해당 카드 목적의 필수 근거가 충분한 이유를 기록한다. 자동 통합만으로 기존 P05 후보를 사람 검토 완료·외부 사실 검증으로 승격하지 않는다.

개인 `analyst_memos.jsonl`은 같은 카드·원문·계산/대사·가정 참조를 사용한다. agent 초안·사람 채택/수정·검토 완료를 나누며 실제 작성자가 없으면 미실행이다. 메모 UI나 모든 팀원의 재무 메모 작성을 필수로 만들지 않는다.

## 6. DB 없는 피드백 운영

### 저장과 반영

로컬 검토는 `feedback_events.jsonl`에 append한다. 공유 화면에서는 검토 기록을 파일로 내보내고 소유자가 로컬에서 가져와 검증한 뒤 새 snapshot을 게시한다. 화면에 ‘이 기기의 초안’, ‘파일로 내보냄’, ‘공유 결과에 반영됨’을 구분해 표시한다. 브라우저 저장만으로 두 사람에게 반영됐다고 알리지 않는다.

원래 후보와 카드는 덮어쓰지 않는다. `feedback_id`, `idempotency_key`, source run/card version, actor, action, field, before/after, 근거/사유, 작성 시각, 수신 시각, review/training eligibility를 기록한다. 내보내기는 필요한 구조화 필드와 ID만 포함하고 제한 원문·개인 메모·키를 포함하지 않는다.

자유입력 actor나 브라우저 시각은 인증된 서버 정보가 아니다. `actor_verification=self_declared`와 시간 출처를 보존하고 소유자 확인을 별도 기록한다. 플랫폼 조회 권한과 가져온 파일의 작성자 검증을 혼동하지 않는다.

### 검증과 충돌

- action은 확인/사실 수정/무관/추가조사/가정 수정으로 구분한다.
- 같은 idempotency key는 재가져오기해도 중복 반영되지 않는다.
- 없는 card ID·다른 run·위조된 before 값·허용되지 않은 field·과도한 파일 크기는 거부하고 이유를 남긴다.
- 서로 다른 두 수정이 같은 이전 버전을 대상으로 하면 충돌 후보를 만들고 소유자가 채택/병합/보류한다. 마지막 파일로 덮어쓰지 않는다.
- 기록은 새로고침·서버 재시작 후 재조회되며 단일 로컬 writer 또는 파일 잠금·원자적 저장으로 손상을 방지한다.
- 피드백은 gold가 아니라 검토 후보다. test feedback·연습/adaptation은 현재 학습 주기에서 격리한다.

자동 공동 저장은 현재 기본 범위가 아니다. 추후 요구가 생기면 인증된 서버·영속 파일 저장·동시성·백업·권한을 실제 구현해야 하며, 정적 사이트에 버튼만 추가해 구현됐다고 표현하지 않는다.

## 8. 산출물과 실행 인터페이스

`artifacts/us_equity/p7/runs/<run_id>/`에 입력 snapshot, 설정, stage별 결과 참조, 카드/연결표, validation, 관측/비용, 사용성·인계, 사이트 게시 기록을 저장한다. 검토 이력은 `artifacts/us_equity/p7/feedback/` 아래 append 이력으로 보존하고 run에는 사용한 feedback version/hash를 고정한다.

추가 CLI 계약 제안은 `p08_run.py`(설정·출력 run-dir·resume), `p08_import_feedback.py`(파일·허용 run·검증/충돌 정책), `p08_verify_package.py`다. 아직 존재하지 않는 명령은 실제처럼 안내하지 않는다. 구현 후 CLI 도움말·내 PC 실행·오류복구·내보내기/가져오기·재게시 절차를 `operator_guide.md`에 실제 명령으로 적는다.

현재 `web/p05/server.py`의 실행 버튼은 P05용이다. P08 연결 후에는 버튼이 수행하는 단계와 결과 위치를 갱신하고 실제 서버 테스트를 한다. 공유 사이트에는 로컬 실행 방법을 보여주되 PC의 프로세스를 원격 실행하는 버튼으로 표현하지 않는다.

## 9. 필요한 검증

- 같은 문서·같은 설정 재실행에서 동일 논리 카드가 중복되지 않는다.
- 중간 stage 장애·한 항목 오류 후 resume 결과가 완전 실행과 의미상 같다.
- 카드 0건은 정상 해당 없음·입력 없음·처리 실패를 구별한다.
- 숫자/기간/정의·관계 방향·시점/모드·계산/보류 사유가 카드에서도 유지된다.
- 서로 다른 피드백·중복 가져오기·오래된 카드 버전 충돌을 보존하고 해결 이력을 남긴다.
- 새로고침·프로세스 재시작 후 로컬 확정 기록이 유지되고 원래 예측을 볼 수 있다.
- 원문의 명령문·피드백 HTML/스크립트를 실행하지 않는다. 로컬 API는 허용 endpoint/경로·요청 크기·동일 origin 정책을 유지한다.
- private 경로·임의 파일·키·원문 prose를 정적/API 응답과 배포 archive에서 노출하지 않는다.
- 비용 미측정은 null/NA이며 외부 호출 0건과 전체 운영 비용 0원을 구분한다.
- 연습·feedback·개인 메모를 독립 test나 사람 gold에 자동 유입시키지 않는다.

브라우저가 가능하면 처음 보는 사람이 따라갈 목록→상세→근거→검토→내보내기 흐름과 좁은 화면을 확인한다. 도구가 없으면 browser QA는 미실행으로 남기고 소스/API 검증과 구분한다. 기존 P04/P05 package 보존도 확인한다.

## 10. 종료와 다음 단계 전달

**개발 종료:** 허용 입력에서 batch→카드→로컬 검토 이력→안전한 게시 결과가 실제 연결되고 실패/재개·중복/충돌·영속 파일을 검증했다. [사이트 업데이트 계약](SITE_PHASE_UPDATE_CONTRACT.md)에 따라 같은 사이트의 게시 성공과 현재 접근 범위를 확인한다.

P09에는 코드/설정/카드/게시 버전, 실제 입력 범위, 연습·feedback 노출 이력, 단계별 시간/호출·측정 여부, 데모와 오류복구 방법을 전달한다. 사람 사용성·작성자 외 재실행이 미완료면 별도 항목으로 남긴다. 미구현 원격 실행·공동 자동 저장·학습 모델을 운영 기능으로 안내하지 않는다.
